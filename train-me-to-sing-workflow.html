Train Me To Sing: Build Workflow

How a local model and a multi-agent loop build the app: the decisions, why they were made, and how they worked out · 14 Nov 2026

Train Me To Sing is a pitch-training web app for a beginner singer. This doc covers how the app gets built rather than the app itself. A 12-epic plan is run by a scripted loop. A coder agent and two reviewer agents work through each epic in turns, and a human steps in only at set points. The loop can run on Claude or on a local Qwen model served from a 32 GB Mac. The local model needed a translation gateway and some careful memory management to survive multi-hour runs.

1System at a glance

A Node driver (harness/run-epics.mjs) owns all state. It starts each agent as a separate headless Claude Code session (claude -p). A run profile decides where those sessions send their model calls. By default they go to Anthropic. With --local they go to a LiteLLM gateway, which forwards them to Qwen running under MLX on the same machine.

Figure 1. The driver is plain code, and the agents do the work. The model endpoint is set by a profile, so the loop is the same on either backend.
Key decision: a profile file, not a shell aliasThe owner already had a claude-local alias. The driver launches claude itself, though, and aliases exist only in interactive shells. So harness/profiles/local.json carries the same environment and applies it to every agent session, including subagents. The gateway key is read from a file at run time, so it never lands in the repo or in the logs.

Why this model

  • Fits the machine. At 4-bit the weights take about two-thirds of 32 GB. That leaves room for context, and nothing larger would.
  • Fast enough to run agents. With ~3B active parameters, each token costs about as much as a small dense model, while a 35B-class model's knowledge stays available. Agents make 50–100 tool calls per run, so per-token speed sets the wall-clock time.
  • Follows strict formats. The reports must pass a validator (exact verdict lines, finding ids, counts). A smaller model would free up memory but costs this ability, so that option was ranked last among the memory fallbacks.
Constraint that shaped the agent design: text only (an endpoint limit, not the model's)A single image in a conversation makes every later request fail with 404 Only 'text' content type is supported. In local mode, the guard hook blocks reads of images and PDFs (TMTS_NO_IMAGES=1). The UI reviewer checks screens through page text, the accessibility tree and measured styles instead, and lists whatever it could not judge by eye under "Not verified" for the human.

3Hosting with MLX

The model is served by mlx_lm.server, Apple's MLX inference server. It exposes an OpenAI-compatible /v1/chat/completions endpoint on 127.0.0.1:8080. MLX runs on Apple silicon's unified memory, so the CPU and GPU share one pool and the weights need no copying between them. The same pool also has to hold the prompt cache, the working memory of a request, and every other app on the machine. Section 5 deals with that.

4LiteLLM: the translation layer

Claude Code speaks the Anthropic Messages API (/v1/messages), and mlx_lm.server speaks OpenAI chat completions. LiteLLM runs as a local proxy on :4100 and translates between the two. Claude Code only needs ANTHROPIC_BASE_URL pointed at it.

A trivial "hello" would pass even when the server can't handle an agent-sized prompt. A full-size request surfaces a dead gateway, a missing model or an out-of-memory condition in seconds, instead of 40 minutes into a coder run. The driver also stops at once on model API errors rather than retrying into a broken server.

5Avoiding out-of-memory failures

The problem

To save re-reading the same prompt, mlx_lm.server keeps a copy of each conversation's processed prompt (its KV cache) after every request. Left alone, this cache grows until memory runs out. The server log then shows Insufficient Memory, and every later request fails with 404 generation thread died. During E02, swap grew from 1.1 GB to 6.3 GB.

Figure 2. About 6 GB sits between the weights and the GPU ceiling. Two saved copies of the largest agent's conversation take about 3 GB of it.

The root cause

The server already has a --prompt-cache-bytes flag. Reading mlx-lm 0.32.2 showed that the flag is applied only in the batched code path. The sequential path, the one this setup actually uses, builds the cache without a byte limit. So the flag looked like a cap but did nothing here.

What was done, and why

DecisionWhat it doesWhy this and not the alternative
Hard MLX limits
TMTS_MLX_MEMORY_GB=26, TMTS_MLX_BUFFER_GB=1		Sets mx.set_memory_limit and mx.set_cache_limit before the model loads.26 GB sits above the 20.4 GB of weights and under the 26.8 GB Metal ceiling, so MLX fails inside its own limit instead of taking the machine down. Freed buffers go back to the OS instead of being hoarded.
Make the byte cap real
2 conversations, 4 GB		The launcher swaps the server's cache class for one built with max_bytes, read from the server's own flag.The fix is a small, targeted patch that fails on version mismatch. Forking mlx-lm would be a maintenance burden. 4 GB covers two copies of the largest agent (≈ 3 GB) with margin.
Flush after every agent
POST /flush		Empties the cache, runs gc.collect() and mx.clear_cache(), and logs Flush: N sequences, X GB released.Every agent starts a fresh conversation, so the saved cache is never reused across agents. The only cost is re-reading a 12–15k-token prompt, which takes well under a minute against agent runs of 6–51 minutes. A failed flush is logged as a warning and never stops the loop.
Run reviewers one after the other
serialReviews: true		The plan and UI reviewers run in sequence in the local profile.Running them in parallel would hold two growing conversations at once, and the server serves one request at a time anyway, so parallelism saved no time.
Agent-sized preflightA 16k-token check before each epic.Catches an under-provisioned server before an agent spends 40 minutes of work against it.
ResultAfter the change, the E03 run's server log shows a peak of 0.57 GB for two saved conversations, far under the 4 GB cap. Each flush released 0.68 GB. The driver logs one line per agent, for example E03 T1 coder: model cache emptied (2 saved, 2.91 GB).
If it still fails: fallbacks, cheapest first
  1. Close memory-heavy apps. CPU and GPU share memory.
  2. Restart the server and rerun the same command. The driver resumes from files on disk.
  3. Lower the limits, or raise iogpu.wired_limit_mb (≤ 26000).
  4. Use a smaller model. This is last because format adherence matters.

Why split it this way: planning and harness design are done once and are expensive to get wrong, so the strongest models did them. Epic execution is repetitive, long-running and well specified, so it can go to a free local model, as long as the plan is precise and the harness checks the output mechanically.

6.2 Planning documents as contracts

The plan is written for agents to execute without asking questions. 01-architecture.md overrides any epic it conflicts with. Each epic file has the same sections: Goal, What you will review, Depends on, Scope, Specification (files, signatures, behaviour), Tests, and a Review script for the human. Every epic ends in something a person can open and check.

Figure 3. The architecture is designed for agents: small pure modules that unit-test easily, boundaries a linter can enforce, and fakes for hardware an agent cannot use.

SUMMARY.md is the one file the owner needs to read. It follows a fixed template, and the validator checks it:

  • What was accomplished: screens and features, in plain language
  • Changes made during review: one line per blocking fix
  • How to test it: numbered steps with expected results, using the real routes and commands
  • Not verified by the agents: mic, speakers, iPhone
  • Known issues and deferred items
  • For the owner to decide

Findings carry stable ids (UI-E02-T1-01), so a reader can trace any change from the review that raised it to the fix.

6.6 When and how the human is in the loop

The loop stops and asks
  • 10 turns pass without both reviewers approving
  • An agent reports BLOCKED - NEEDS OWNER (the plan conflicts, or a decision only the owner can make)
  • The coder and a reviewer dispute the same blocking finding two turns running
  • An agent's file fails validation twice
  • A model or API error, or a failed preflight

E02 hit this on its first attempt. The local coder's run failed and its report failed validation twice, so the driver stopped and wrote NEEDS-INPUT. The owner restarted the model server, noted it in OWNER-NOTES, and the run resumed.

The owner steers and verifies
  • OWNER-NOTES.md: read by every agent each turn, and overrides the epic file
  • ui-requirements.md: only the owner may edit it (hook-enforced). The UI reviewer re-reads it every turn
  • Review script: steps no agent can do, such as hearing pitch, singing into a real mic, or checking iPhone Safari
  • FOR-OWNER.md: questions and proposed requirement changes collected at approval
  • Redo an epic by resetting its status and adding notes

The design puts the human on judgment and physical verification, not on babysitting. Agents can't hear audio or use a microphone, so every summary ends with an explicit list of what only the owner can confirm.

7Guardrails: rules as code

The main design principle is that the loop does not rely on models following instructions. Prompts describe the rules, and code enforces them. This matters most for the local model, which follows formats less reliably than Claude.

What can't be enforcedReview quality. A reviewer can still approve too easily. The validator demands evidence (coverage tables, screenshots, answered findings) but can't demand judgment. The owner's review script is the backstop.
A gotcha worth knowingHeadless claude -p ignores the project's .claude/settings.json, including the allowlist and the guard hook, until the folder has been trusted interactively. Without that step every agent would be denied npm and git. The driver detects this and stops with instructions before doing any work.

What the local run taught the harness

Almost every hardening change came from the first local run. Each failure on Qwen turned into a general fix that helps both backends:

Fail early

A preflight with an agent-sized prompt, and an immediate stop on API errors, replaced finding out 40 minutes in.

Bound resources

Memory limits, a working cache cap, a flush per agent, and serial reviews. A multi-hour all --local run is now viable.

Adapt the role

The UI reviewer works without vision and says so explicitly. The gap goes to the human rather than being hidden.

Bottom lineWith a precise plan and mechanical enforcement, a local model reached the same outcome as Claude: approved in two turns, with a usable summary and test steps. It was slower and needed more review catches, and part of the slowdown has a fixable cause (section 9). The investment that made this work was the harness, more than the model: contracts up front, rules in code, and the human placed where judgment and physical testing are needed.

9Open issues

Local runs are slow: agent steps take 1.5–2 minutes, and the E02 turn-1 coder ran for 51 minutes. Two leads are open. The server log settles which one matters more: across the 31 requests in the current E03 run, 59% of the time went to prefill (re-reading the prompt) and 41% to generating output.

9.1 The prompt cache is never reused

Every request prefills from token 0. The progress lines run 512 → 32,467, then 512 → 33,304, and so on up to 56,007, even though each step adds only a few hundred tokens. The cache holds 2 sequences at 0.57 GB throughout, so saved conversations are never matched or extended. A 40k-token conversation costs about 80 s to re-read on every step, and that cost grows as the conversation grows. If prefix reuse worked, a step would only prefill its new tokens, and most of the red bar would disappear.

Strongest lead: the model's hybrid architecture makes cache reuse all-or-nothingQwen3.6 has 40 layers. 30 use linear attention, whose cache (ArraysCache) holds a running state rather than per-token entries, so it can't be rewound. In mlx-lm 0.32.2, LRUPromptCache.fetch_nearest_cache can reuse a saved conversation in two ways: when it is an exact prefix of the new prompt, or by trimming a longer saved one back to the common prefix. The second needs every layer's cache to be trimmable, so it never applies to this model. The saved sequence is the old prompt plus the tokens the model generated, including its <think> reasoning and tool calls. If the next request re-renders that assistant turn even slightly differently (reasoning dropped or reformatted, tool-call JSON re-serialized), there's no exact prefix and no partial reuse. Prefill starts from 0, which is exactly what the log shows. The hypotheses below are the likely sources of that difference.

9.2 "Move all experts to CPU/RAM, keep the KV cache on the GPU"

What the advice means. It comes from llama.cpp users on PCs with a discrete GPU, using --n-cpu-moe / --cpu-moe or -ot "exps=CPU". In a mixture-of-experts model, the expert feed-forward weights are most of the 35B parameters, but only a few experts (~3B parameters) run per token. On a PC, VRAM is small and separate from system RAM. Putting the experts in system RAM and computing them on the CPU frees VRAM for attention and a large KV cache. Each token touches so few expert weights that the CPU can keep up, and people report 20–40 tok/s where the model wouldn't otherwise fit.

Figure 6. The advice solves a problem this machine doesn't have.

Why it probably doesn't apply here, and what to take from it instead:

  • No memory is freed. On unified memory, the experts sit in the same RAM whichever processor computes them. The real limits, the 26.8 GB GPU working set and 32 GB in total, don't change.
  • MLX can't do it. mlx_lm.server runs every operation on one device (the GPU) and has no per-expert placement. Trying this means switching to llama.cpp with a GGUF build of the model, and there the experts would run on the slower CPU cores, sharing the same memory bandwidth.
  • The GPU path should already be able to pass 30 tok/s. Generation in a mixture-of-experts model is limited by memory bandwidth. At 4-bit, each token reads roughly 2 GB of active weights, so ~150 GB/s gives a ceiling of several tens of tok/s. Generation speed hasn't been measured directly yet. If it turns out well below that, the likelier causes are swapping (swap grew to 6.3 GB during E02) and the cost of attention over 40–56k-token contexts, not where the experts live.
  • The goal behind the advice still applies: keep weights and KV cache from competing for memory. On this Mac, the tools for that are the memory limits already in place, --kv-bits 8 (halves the cache, untested on this model), raising iogpu.wired_limit_mb, and closing other apps during runs.

9.3 Image review for the UI reviewer

Is it the model or the endpoint? It's the endpoint. The checkpoint is multimodal: its config declares Qwen3_5MoeForConditionalGeneration with a vision_config, it includes 333 vision-encoder weight tensors, and it ships image and video preprocessor configs. mlx_lm.server loads only the language model and rejects any non-text content (server.py:233, "Only 'text' content type is supported."). That's why one screenshot broke every later request, and why the guard hook now blocks image reads.

9.4 Thinking mode: on today, but not chosen deliberately

Current state: on, by default. The model's chat template opens a <think> block on every reply unless enable_thinking=false is passed. Nothing in the stack passes it: there's no --chat-template-args on the server and no per-request chat_template_kwargs from LiteLLM. Claude Code reports 0 thinking tokens, but that only reflects its own accounting. The server returns the reasoning in a separate reasoning field, so the model is reasoning on every step. Whether that text is passed back to Claude Code, and from there back to the model on the next step, hasn't been checked. If it isn't, that is hypothesis 1 in 9.1.

Trade-off. Thinking improves multi-step logic and spec-checking, but every reasoning token is generated output, and generation is 41% of request time. It may also be what breaks cache reuse. The template's own switch makes it a per-request choice:

Agent / stepRecommendedWhy
epic-coder, turn 1Thinking onBuilds a whole epic from a spec: design, multi-file changes, test failures. This is where reasoning pays for itself
plan-reviewerThinking onChecks logic and edge cases against the plan. The E02 turn-1 catches (missing smoothing, wrong clock) are reasoning work
epic-coder, turn 2+Try offFixes are narrow and named by finding id. Turn it back on if fix turns start failing review
ui-reviewerOffMostly runs scripts, reads output and fills in a template. Revisit once it can see images (9.3)
epic-summarizerOffSummarizes files into a fixed template
Preflight checkOffIt only checks that the model answers

How to wire it (untested): define two model names in litellm.yaml, qwen3.6 (thinking) and qwen3.6-fast with extra_body: {chat_template_kwargs: {enable_thinking: false}}. Point each agent at one through its model: frontmatter or the profile's per-tier aliases. Keep sampling settings per mode: the checkpoint's defaults (temperature 1.0, top_p 0.95, top_k 20) assume thinking mode, so check Qwen's recommended non-thinking values before switching.

Suggested order(1) Instrument and fix cache reuse (9.1). Checking whether reasoning makes the round trip there also settles 9.4's open question. (2) Split thinking per agent (9.4), which is cheap and lowers generation time. (3) Move to an image-capable server (9.3). (4) Measure generation tok/s before spending time on expert offload (9.2).
